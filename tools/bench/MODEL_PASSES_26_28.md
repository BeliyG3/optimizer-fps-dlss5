## Как это работает в перехватчике

Host handle остаётся ключом существующего proxy mapping. Первая реальная feature остаётся в
`realHandle`; для проходов 2 и 3 создаются независимые реальные feature-18 handles через тот же
`CallCreate`/forwarder, с work-размерами и восстановлением параметров host. Дополнительные features
не возвращаются host и не проходят через ветку второго внешнего потребителя NR.

Создание выполняется на отдельном кадре без evaluate. На нём переносится уже готовый результат;
при первоначальной инициализации, когда результата ещё нет, показывается исходный цвет host.
Это явный setup-кадр, а не ошибка evaluate. В логе есть `model passes setup frame`.
Перед каждым следующим проходом результат копируется в отдельный staging, чтобы модель не читала
и не писала один ресурс. Каждый handle сохраняет собственную историю. При неудаче дополнительного
evaluate восстанавливается последний успешный результат, а предупреждение остаётся в статусе.

При изменении extent/release handles проходят через `BuryReal` с существующими fence gates,
включая gate фоновой работы. Staging, скрытые temporal-машины и снимки идут в общий graveyard.
Неудачное создание не повторяется каждый кадр: следующая попытка — после изменения настройки/extent.

В spread-режиме отдельная скрытая temporal-машина хранит каждый незавершённый результат. На
следующем кадре его вклад переносится на текущую сцену; выбранная стадия получает свою цепочку
motion vectors. Residual каждой стадии измеряется относительно сохранённого исходного кадра.
Промежуточные стадии не публикуются. До завершения переносится предыдущий полный цикл; до первого
полного цикла показывается исходный кадр. N повышается до числа проходов. При N больше числа
проходов оставшиеся кадры только переносят готовый результат.

**Особенность режима 3:** при включённом spread выполняется синхронное расписание на host queue,
по одному evaluate на кадр; overlay объясняет, что background queue не используется. При выключенном
spread вся цепочка выполняется на background queue, как один фоновый job.

  доступного числа проходов проверены кодом, не реальным OOM-тестом.
- UI собран, INI проверен тестами и bench; ручная визуальная проверка элементов ReShade не проводилась.
- Стресс переключает layout, а не число проходов/checkbox во время работы. Горячая смена этих двух
  настроек и переключение async ↔ spread отдельно не прогонялись.
- Нет тестов в играх, измерений VRAM allocator или проверки всех host-форматов/subrects.
- До первого готового результата есть явный raw setup/прогрев; обещания «модель видна с первого кадра» нет.
